## 这次完善了什么

原版只有一段故障倒计时。新版保留这一兼容路径，并为新场景增加两种维修流程：

- MINOR（一般故障）：直接现场维修，完成后原车继续原任务。
- ASSISTANCE_REQUIRED（需外援故障）：等待救援 → 现场维修 → 原车继续原任务。

救援是仿真时间计时，不存在真实救援车辆、赶赴路线、换车或拖车。两种等级都是任务书中同一类“车辆故障”，不重复计算事件类别。

自动故障概率沿用 2%/小时。新规则 breakdown-v2 下，一般故障权重 70%，维修 30～60 分钟；需外援权重 30%，等待 30～60 分钟、维修 60～120 分钟。所有参数都是演示假设；时间是仿真分钟，不是现实等待分钟。

## 手动触发示例

POST `/api/simulation/random-events/trigger`，使用当前存在活跃驾驶任务的真实 vehicleId 替换示例值。

一般故障：

```json
{"eventType":"VEHICLE_BREAKDOWN","vehicleId":12,"breakdownLevel":"MINOR","repairMinutes":60}
```

需外援故障：

```json
{"eventType":"VEHICLE_BREAKDOWN","vehicleId":12,"breakdownLevel":"ASSISTANCE_REQUIRED","rescueWaitMinutes":30,"repairMinutes":90}
```

兼容的旧版请求：

```json
{"eventType":"VEHICLE_BREAKDOWN","vehicleId":12,"durationMinutes":60}
```

新阶段字段不与 durationMinutes 混用；拥堵请求不传故障等级和阶段时长。参数错误返回 400，活跃事件或车辆业务状态冲突返回 409。

## 如何理解恢复

等待救援和维修期间均为 BREAKDOWN，速度为 0，货物和原任务保留。阶段是事件的处理进度，不是另一份车辆业务状态机。

plannedEndTime/resolvedTime 表示模型预计/实际的维修结束时刻；recoveryProcessedTime 表示仿真主循环真正处理恢复的时刻。比如 00:00 故障、等待 30 分钟、维修 90 分钟，则 02:00 模型修好；若 02:30 才处理，只计入 02:00～02:30 的驾驶工作量。

recoveryOutcome 必须与阶段一起解释：RECOVERED 表示维修计时闭环结束，不保证车辆仍能恢复原任务；若原任务失效或车辆已被其他流程改变，应保留原因而不是覆盖新状态。

旧 delaySeconds 仍是事件持续时长，不是相对无故障任务的精确晚到时间。waiting/repair 时长也不直接充当运输成本。

## 兼容与后续讨论

新创建场景保存 breakdownPolicy；旧保存或导入场景没有该字段时继续原机制，不自动改变旧实验。固定种子可复现相同场景下的故障等级/阶段时长，但单车事件仍受车辆状态与 ID 影响，不承诺跨算法一致事件序列。
