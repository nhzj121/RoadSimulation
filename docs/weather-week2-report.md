# 第二周：天气与可回放运输环境交接报告

更新：2026-09-12。代码在 `feature/random-transport-events-week1` 功能分支；未合并、未推送。后端仍为 8080，前端仍为 5173，未将本机数据库密码写入共享配置。

## 组会可以这样讲

这周把上周的单车随机事件扩展为“全地图天气＋统一驾驶进度”。天气独立保存，不给每辆车复制天气事件。驾驶按剩余正常行驶工作量计算，雨天、拥堵共同减速，故障暂停；路程完成就能到达，不必等雨停或拥堵结束。

现在可以选择晴天基线、天气演示、固定种子自动场景，导出和重新导入同一张天气时间表。每次运行有独立编号，手动干预有标记，重置会归档本次结果并保留场景。前端读取后端的速度系数和驾驶进度，不再自己决定任务完成。

后端闭环已在隔离 MySQL 数据库上跑过，天气面板完成了浏览器交互检查。但联网地图资源在当前验收环境被拦截，不能把这次结果说成“完整地图演示已验收”；多站带货任务的端到端验收也需补做。

## 落地接入点

| 位置 | 作用 |
|---|---|
| `WeatherScenario` / `WeatherRun` | 分别保存环境时间表与一次运行、实验关联、干预标记和归档结果 |
| `WeatherEnvironmentService` | 创建、校验、装载、查询天气；独立随机源生成序列；回放读取已保存序列 |
| `DrivingProgress` / `DrivingProgressService` | 按运行、任务、驾驶阶段、路段区分剩余工作量；按天气和事件边界分段积分 |
| `SimulationMainLoop` | 先结算上一段驾驶，再处理事件和状态转换，再初始化新驾驶阶段 |
| `StateTransitionServiceImpl` | 驾驶完成门禁；天气模式不对驾驶强制截断到 60 分钟；装卸仍按原时长 |
| `SimulationController` / `TransportLifecycleService` | 拒绝提前到达或跳过装载；多站到达需匹配阶段及路段 |
| `TransportMonitorService` | 返回当前天气、场景/运行编号、有效系数、剩余工作量和完成时间 |
| `WeatherPanel.vue` / `MapContainer.vue` | 场景入口、导入导出、锁定提示；读取后端进度校正动画，刷新恢复运行或暂停的视图 |

旧 API 不传 `scenarioId` 保持旧行为；新前端默认选择天气演示。算法对比循环未启用新天气模型。

## 当前演示参数（仿真假设，待组内确认）

- 晴/雨/雪/雾系数：1.0 / 0.8 / 0.5 / 0.6。
- 自动天气：独立种子，默认每 120 仿真分钟抽取一次，生成 24 小时；权重 50% / 25% / 10% / 15%。时间表结束后晴天、系数 1。
- 拥堵：每小时概率 0.08，持续 30～90 分钟，系数 0.4。
- 故障：每小时概率 0.02，持续 60～120 分钟，系数 0，维修后继续原任务。
- 每步概率为 `1 - (1 - hourlyProbability)^(stepSeconds / 3600)`，不是每轮直接使用小时概率。
- 基线和演示预设关闭单车自动事件；AUTO 预设开启，界面明确显示开关。手动触发会将本次运行标记为含人工干预。

雨天＋拥堵的有效系数为 `0.8 × 0.4 = 0.32`；故障优先为 0。用户动画倍速仍独立保留。

## 演示步骤与交接

1. 正常启动项目，使用已有 POI 数据（空库会遇到已有主循环初始化问题）。
2. 天气面板选择默认演示，启动后核对场景 ID、运行 ID、自动事件关闭提示。
3. 到雨天观察有效系数 0.8；选择正在驾驶的车手动拥堵，核对 0.32；另一辆车故障应显示停驶、系数 0。
4. 检查提前到达拒绝、车辆进度、维修恢复；天气未结束但短程工作量完成，应正常进入卸货。
5. 暂停并刷新页面，核对位置及暂停状态；恢复后继续原运行。地图恢复须在高德可访问环境中人工确认。
6. 导出场景和运行记录，再重置；导入同一场景重跑，核对天气表相同、运行 ID 不同。

HTTP 与 Java 调用示例见 `weather-sandbox-handoff.md`。三套完整可导入场景见 `examples/weather-{baseline,demo,auto}.json`。

## 值得组会决定的问题

1. 参数是否采用当前演示值？目前不是老师指定、道路实测或气象研究结论。
2. 原驾驶时长部分固定 30 分钟，主循环约 30 仿真分钟一步；是否优先改为道路距离驱动、缩小步长？必须区分模型完成与实际处理时间。
3. “延误”用什么口径？旧 `delaySeconds` 是事件持续时长；新 `affectedSeconds` 是受影响时间，`lostWorkSeconds` 是损失的正常驾驶工作量，都不是最终任务相对无事件基线的精确晚到时间。
4. 沙箱是否先只比较固定天气、关闭单车自动事件？同天气下路线和出发时刻不同，受影响程度不同是合理的；现有单车事件依赖车辆状态与 ID，不承诺跨算法完全相同。
5. 下一阶段优先补联网地图、多站带货验收，再决定区域天气、故障换车或实验事件预生成。进程崩溃后恢复正在运行的场景也尚未实现；目前支持页面刷新、暂停/恢复和正常重置归档。

本周不改成本函数，不实现沙箱页面、算法对比循环接入、区域天气或换车重调度。
