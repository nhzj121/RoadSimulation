# 随机运输事件第一周实施报告

## 1. 本周结论

本周已完成“交通拥堵 + 车辆故障”的最小闭环。两类事件都可通过接口或前端面板手动触发，也已具备按固定种子自动生成的能力（默认关闭）。后端使用仿真时间持久化事件并控制任务能否推进，前端根据后端事件将单车减速或暂停。

本周未实现换车重调度、区域/路段拥堵、天气、货损、缺货和成本公式调整。

## 2. 功能在项目中的落点

### 2.1 后端事件生命周期

```text
每次普通仿真 tick
  -> 解除已到期事件
  -> 按配置尝试生成自动事件
  -> 车辆状态 tick
  -> 状态转移前检查活跃事件门禁
```

- `TransportRandomEvent` 记录事件类型、来源、关联车辆/任务、仿真开始与结束时间、速度系数、延误时间及恢复状态。
- `TransportRandomEventService` 是事件触发、解除、查询和状态门禁的统一入口。
- `SimulationMainLoop` 在车辆状态更新前执行事件 tick。
- `StateTransitionServiceImpl` 在原有 60 分钟状态截断前检查事件，防止故障或拥堵期间误推进。
- 仿真重置时先删除事件，再删除 Assignment，避免外键和残留影响。

### 2.2 两类事件的影响

| 事件 | 后端状态 | 任务推进 | 前端动画 | 到期处理 |
| --- | --- | --- | --- | --- |
| 交通拥堵 | 保持原驾驶状态 | 暂停当前驾驶阶段结算 | 速度默认乘 `0.4` | 速度恢复为事件系数 `1` |
| 车辆故障 | 切换为 `BREAKDOWN` | 保留活跃 Assignment，拒绝到达结算 | 速度乘 `0`，车辆暂停 | 恢复故障前状态和剩余状态时长 |

前端的最终动画速度为“用户全局速度 × 单车事件速度”，事件解除不会覆盖用户设置的全局速度。

### 2.3 公开接口

- `POST /api/simulation/random-events/trigger`
- `GET /api/simulation/random-events/active`
- `GET /api/simulation/random-events/history?limit=50`

手动触发示例：

```json
{
  "eventType": "VEHICLE_BREAKDOWN",
  "vehicleId": 12,
  "durationMinutes": 60
}
```

`durationMinutes` 可省略，显式传入时必须在 30–240 分钟之间。车辆无活跃任务、不在驾驶状态、或已有活跃事件时，接口会拒绝请求。

运输监控接口同时新增：

- `summary.activeEventCount`
- `vehicles[].activeEvent`
- 顶层 `activeEvents`

## 3. 演示步骤

1. 启动后端和前端，开始普通仿真并等待产生运输任务。
2. 在“随机运输事件”面板选择处于“前往装货点”或“运输中”的车辆。
3. 触发“拥堵”：观察目标车辆降速，其他车辆不受影响；调整全局速度，两个速度系数仍同时生效。
4. 待拥堵解除或选另一辆车，触发“故障”：观察车辆暂停且状态显示为红色“故障”。
5. 故障期间调用 `/api/simulation/vehicle-arrived`，应返回 HTTP 409。
6. 仿真时间到期后，车辆恢复原状态并继续原任务。
7. 重置仿真，确认活跃事件、历史事件及动画影响都被清除。

## 4. 验证结果

- 随机事件定向单元/控制器测试：9 个通过。
- 覆盖内容：固定种子可复现、小时概率换算、拥堵门禁、故障状态恢复、手动触发成功/冲突、活跃查询、到达请求 409。
- Maven 编译：通过。
- `npx --no-install vite build`：通过，1508 个模块完成构建。
- 浏览器交互回归：未执行。当前会话未提供 Browser 插件，项目也未配置 Playwright；为避免临时安装浏览器依赖改变项目环境，本周把真实页面操作保留为人工演示验收项。

项目全量 Maven 测试在本功能之前已有两个基线问题，本周未改动：

1. `CostBaselineCalibrationIT$BaselineCalibrationApplication` 使 Spring 测试检测到多个 `@SpringBootConfiguration`。
2. `GetCostServiceVehicleCostTest` 期望值为 `7.195`，当前实际值为 `7.145`。

前端原有 `npm run build` 会先调用已失效的 `vue-tsc --noEmit`，因此本周按计划使用 Vite 直接验证生产构建。

## 5. 已识别的技术问题

1. **60 分钟状态截断**：现有状态机会强制截断过长状态。本周通过在截断前增加事件门禁规避，但长期需要明确该截断是业务规则还是临时保护代码。
2. **前后端双时钟**：后端以仿真时间为权威，前端车辆位置仍由本地动画帧积累。刷新页面、卡顿或高倍速时可能有位置偏差。
3. **自动概率待标定**：当前默认交通拥堵 `0.08/小时`、车辆故障 `0.02/小时`，自动触发默认关闭，避免未确认概率影响现有仿真。
4. **对比实验尚未接入**：普通仿真已接入，`DispatchComparisonExperimentServiceImpl` 的独立循环本周不处理事件。
5. **延误尚未进入成本**：目前只记录和展示 `delaySeconds`，不改动运输成本函数。

## 6. 组会需要确认的问题

1. 事件概率按“每车每小时”定义是否合适？两个默认值是否需要按现实数据或演示需求标定？
2. 故障长期策略是“等待维修后继续原任务”，还是需要“换车/重新调度”？
3. 现有 60 分钟状态截断应删除、改为配置，还是保留？
4. 算法对比实验是否必须共用一组预生成的事件序列，以保证算法之间可公平比较？
5. 下一类事件优先做天气、货损还是缺货？如果目标是强化调度算法对比，建议优先做“故障后换车”和“区域拥堵”。

## 7. 下一步建议
