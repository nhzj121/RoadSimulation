# 车辆报废与换车续运交接说明

更新日期：2026-09-27  
功能分支：`feature/random-transport-events-week1`  
范围：在一般故障、需外援故障之外，增加“需换车故障”；不实现救援车路线、换车费用、精确分段里程或算法对比实验。

## 一、这次具体做了什么

### 1. 增加第三种故障等级

故障事件仍然属于 `VEHICLE_BREAKDOWN`，新增等级 `REPLACEMENT_REQUIRED`。它的处理阶段是：

1. `WAITING_REPLACEMENT`：原车已经报废，但还没有合适的空闲车；系统每个仿真循环重试。
2. `REPLACEMENT_PREPARING`：已经锁定一辆替换车，等待固定交接时间。
3. `REPLACED`：交接完成，新车继续原任务。

原车状态为 `SCRAPPED`，替换车准备期间为 `RESERVED_REPLACEMENT`。这两个状态都不会被普通状态机自动改回空闲，也不会继续行驶；仿真重置后才恢复。

### 2. 保留同一个任务，不重新创建货物流程

换车不是新建 Assignment，而是在交接时把原 Assignment 的承运车辆改为替换车。因此以下数据保持不变：

- Assignment ID；
- 已完成和未完成的节点；
- ShipmentItem 与货物状态；
- 已经发生的库存变化；
- 当前路段和剩余正常驾驶工作量。

交接时转移车辆坐标、当前 POI、载重、体积和驾驶进度；原车载重/体积清零并保持报废。这样可以避免重复装货、重复扣库存或从第一段路线重新开始。

### 3. 确定性选择替换车辆

候选车必须同时满足：

- 当前为 `IDLE`；
- 没有活跃任务或活跃随机事件；
- 载重、容积都能覆盖剩余任务过程中的最大需求；
- 不是原报废车辆。

选择顺序固定为“载重剩余量最小 → 容积剩余量最小 → 车辆 ID 最小”。容量需求不是只看当前货物，而是从当前载重/体积开始，按未完成节点依次应用装卸变化，取后续最大值。

数据库用带条件的原子更新预留车辆，并记录预留属于哪个事件；两个报废事件不能同时得到同一辆替换车。候选失效时只释放本事件拥有的预留，然后回到等待状态。

### 4. 支持无车等待和固定时间交接

没有合适车辆时，事件保持活跃，`plannedEndTime` 允许为空，任务不会直接失败。选到车辆后默认等待 60 个仿真分钟（手动可设整数 30～180 分钟），到时在同一事务内完成任务所有权和运行状态交接。

新建 `breakdown-v3` 场景规则：总故障概率仍为 2%/小时；发生故障后，一般故障 60%、需外援 30%、需换车 10%，自动换车等待为 60～90 分钟。旧 `breakdown-v2` 仍按原 70%/30% 路径，不自动升级。

### 5. 增加可追溯记录和接口字段

事件保存原车、新车、容量需求、选择/就绪/实际处理时刻和最终结果。另有独立的换车尝试记录，用于区分预留、取消和成功交接；运行归档和 JSON 导出包含这些记录。

手动触发示例：

```json
{
  "eventType": "VEHICLE_BREAKDOWN",
  "vehicleId": 12,
  "breakdownLevel": "REPLACEMENT_REQUIRED",
  "replacementWaitMinutes": 60
}
```

换车等级不能与 `durationMinutes`、`rescueWaitMinutes` 或 `repairMinutes` 混用。现有拥堵、旧故障请求保持兼容。

### 6. 前端展示与地图恢复

随机事件面板增加“报废并换车续运”和换车等待时长。界面能区分“等待可用车辆”“替换车准备中”“已由新车接管”和失败原因。

地图绘制身份改为 `assignmentId + vehicleId`。后端把同一 Assignment 改给新车后，前端会清理旧动画、旧 marker 和旧管理器登记，再用新车的后端状态/坐标恢复显示。若路线重绘失败，会持续查询活跃任务并重试，不会因为任务早已标记为已绘制而永久丢失。

非天气模式没有精确驾驶进度快照时，换车恢复采用静态、后端权威显示：使用后端车辆状态、当前位置和当前节点，不在浏览器本地重演装货、卸货或到达。`SCRAPPED` 与 `RESERVED_REPLACEMENT` 在事件结束后仍保持停驶，直到后端真正改变状态。

## 三、本次复审发现并解决的问题

独立审查不是只看测试数量，实际发现并修复了这些边界：

- 替换车曾有旧任务时，新进度可能被旧记录盖住；现按交接时刻排序，并核对运行、任务和驾驶阶段。
- 并发事件可能读到缓存中的“空闲车”；现用数据库原子占用、事件所有权和锁后复核。
- 全局清空持久化上下文会影响同一轮后续任务；现只刷新被预留车辆。
- 交接前未分配任务的候选车原先不出现在监控；现按活跃事件补入。
- 非天气换车曾可能从第一段重放业务动作；现进入静态恢复模式。
- 重绘失败后曾可能不再查询该任务；现保存待恢复身份并持续重试。
- 非天气监控使用 `assignmentIds` 时，已运行原车曾收不到 `SCRAPPED`；现车辆状态按 vehicleId 同步，驾驶进度仍按任务隔离。

## 四、组会需要确认的事项

1. “报废”是仅当前仿真运行有效，还是以后要进入真实资产报废记录？当前实现重置后恢复车辆。
2. 替换车等待 60～90 分钟、故障等级 60%/30%/10% 均为演示假设，是否调整？
3. 没有候选车时应无限等待、任务失败，还是触发跨区域调车/外租车辆？当前实现持续等待。
4. 后续是否计算替换车真实赶赴路线和空驶成本？当前只模拟固定交接时间。
5. 算法对比实验是否需要预生成相同的报废事件与候选资源变化？当前仍不承诺跨算法获得完全一致的单车事件序列。
6. `AssignmentLeg` 是否需要拆分原车和新车各自里程？当前用换车历史记录交接，原路段不拆分。
