# 其他开发者数据库同步操作说明

## 1. 文档目的

本文档用于将其他开发者的本地数据库与当前项目的生产加工链定义保持一致，并说明需要完整数据库一致时的备选方案。

默认推荐使用“定义级同步”：只同步加工链 DAG 定义，不复制他人的仿真运行数据和评价历史。

## 2. 同步范围

### 2.1 推荐：定义级同步

定义级同步将目标数据库规范化为：

| 数据 | 目标数量 |
| --- | ---: |
| `processing_chain` 目标加工链 | 4 |
| `processing_stage` 目标加工阶段 | 15 |
| `processing_stage_input` 具名阶段输入 | 15 |
| `processing_stage_edge` 显式阶段边 | 11 |

该方式不同步：

- 车辆当前状态和位置；
- 运单、货物项、任务和分配结果；
- 路线请求和前端动画状态；
- 评价快照、等待账本和能耗账本；
- 生产计划、生产批次和执行流。

### 2.2 备选：整库完全同步

只有完整导出和恢复数据库，才能使两台电脑的所有业务与评价历史完全一致。整库恢复会覆盖目标数据库，仅适用于可丢弃的开发环境，不是默认同步方式。

## 3. 定义级同步的前置条件

只有同时满足以下条件，才可直接执行兼容迁移：

1. 开发者已拉取包含以下文件的最新代码：
   - `migrate_existing_processing_chains_to_dag_compat.sql`；
   - `create_production_domain_tables.sql`；
   - `create_y_shape_dag_tables.sql`。
2. 目标数据库来自团队之前同步过的基础数据。
3. 4 条目标加工链已存在，且阶段数分别为 `4、4、4、3`。
4. 目标加工阶段尚未建立新的阶段输入和边，或者迁移结果已完整存在。
5. 本地 MySQL 账号对目标数据库具有表结构和数据变更权限。

如果加工链代码、阶段数、阶段顺序或 Goods/POI 主数据不一致，必须停止并进行差异分析，不能直接使用脚本覆盖。

## 4. 推荐操作步骤

### 步骤 1：拉取最新代码

在远程 PR 已合并到 `master` 后执行：

```powershell
git switch master
git pull --ff-only origin master
```

如果迁移文件尚在待合并的功能分支中，应等待 PR 合并，不建议通过复制聊天中的 SQL 片段代替版本化脚本。

### 步骤 2：停止后端

迁移期间必须停止后端、定时任务和手工 API 调用，避免：

- JPA 自动建表与手工 DDL 并发；
- 生产计划在迁移中被释放；
- 仿真循环生成新运单和评价快照；
- 验收数量被并发数据干扰。

### 步骤 3：备份开发者自己的数据库

备份是执行迁移的必要前置条件。可使用 MySQL Workbench 的 Data Export，或在 PowerShell 中调用 `mysqldump`。

示例：

```powershell
mysqldump -u root -p --single-transaction --set-gtid-purged=OFF `
  --result-file="D:/db-backup/vehicle_scheduler_before_dag.sql" `
  vehicle_scheduler
```

路径必须改为开发者自己的可写目录。不要把数据库备份纳入 Git。

### 步骤 4：确认当前数据库

进入 MySQL 客户端后执行：

```sql
SELECT DATABASE();
```

如果结果不是目标库，先显式选择：

```sql
USE vehicle_scheduler;
```

禁止在没有确认 `DATABASE()` 的情况下执行 DDL 或迁移脚本。

### 步骤 5：检查旧加工链基线

```sql
SELECT
    pc.chain_code,
    COUNT(*) AS stage_count,
    COUNT(DISTINCT ps.stage_order) AS distinct_stage_orders,
    SUM(ps.stage_key IS NULL OR ps.stage_key = '') AS blank_stage_keys
FROM processing_chain AS pc
JOIN processing_stage AS ps
  ON ps.chain_id = pc.id
WHERE pc.chain_code IN (
    'CHAIN_WOOD_FURNITURE_001',
    'CHAIN_METAL_FURNITURE_002',
    'CHAIN_METAL_CAR_003',
    'CHAIN_RUBBER_CAR_004'
)
GROUP BY pc.id, pc.chain_code
ORDER BY pc.chain_code;
```

首次迁移前预期：

| `chain_code` | `stage_count` | `distinct_stage_orders` | `blank_stage_keys` |
| --- | ---: | ---: | ---: |
| `CHAIN_METAL_CAR_003` | 4 | 4 | 4 |
| `CHAIN_METAL_FURNITURE_002` | 4 | 4 | 4 |
| `CHAIN_RUBBER_CAR_004` | 3 | 3 | 3 |
| `CHAIN_WOOD_FURNITURE_001` | 4 | 4 | 4 |

如果 `stage_count` 或 `distinct_stage_orders` 不符合，禁止直接迁移。

### 步骤 6：检查新生产域表结构

```sql
SHOW TABLES LIKE 'production_plan';
SHOW TABLES LIKE 'production_plan_node';
SHOW TABLES LIKE 'production_batch';
SHOW TABLES LIKE 'processing_stage_execution';
SHOW TABLES LIKE 'processing_stage_input';
SHOW TABLES LIKE 'processing_stage_edge';
SHOW TABLES LIKE 'production_plan_flow';
SHOW TABLES LIKE 'processing_execution_flow';

SHOW COLUMNS FROM processing_stage LIKE 'stage_key';
SHOW INDEX FROM processing_stage
WHERE Key_name = 'uk_processing_stage_key';
```

如果表或唯一索引缺失，先执行：

```sql
SOURCE <开发者自己的项目路径>/create_production_domain_tables.sql;
SOURCE <开发者自己的项目路径>/create_y_shape_dag_tables.sql;
```

`SOURCE` 是 MySQL 命令行客户端指令，不是标准 SQL。如果使用 IDEA/DataGrip/MySQL Workbench，应使用其“运行 SQL 脚本”功能。

### 步骤 7：检查 Goods 主数据

```sql
SELECT id, sku, name
FROM goods
WHERE sku IN (
    'LOG',
    'PLANK',
    'PANEL',
    'IRON_ORE',
    'STEEL_BILLET',
    'STEEL_PRODUCT',
    'RUBBER_RAW',
    'RUBBER_SEMI',
    'TIRE'
)
ORDER BY sku;
```

应当得到 9 条唯一 SKU 记录。如果缺少或重复，必须停止；不能在没有确定重量、体积等参数时自动伪造 Goods 数据。

### 步骤 8：检查是否已经迁移

```sql
SELECT
    (SELECT COUNT(*)
     FROM processing_stage_input AS psi
     JOIN processing_stage AS ps ON ps.id = psi.stage_id
     JOIN processing_chain AS pc ON pc.id = ps.chain_id
     WHERE pc.chain_code IN (
         'CHAIN_WOOD_FURNITURE_001',
         'CHAIN_METAL_FURNITURE_002',
         'CHAIN_METAL_CAR_003',
         'CHAIN_RUBBER_CAR_004'
     )) AS input_count,
    (SELECT COUNT(*)
     FROM processing_stage_edge AS pse
     JOIN processing_chain AS pc ON pc.id = pse.chain_id
     WHERE pc.chain_code IN (
         'CHAIN_WOOD_FURNITURE_001',
         'CHAIN_METAL_FURNITURE_002',
         'CHAIN_METAL_CAR_003',
         'CHAIN_RUBBER_CAR_004'
     )) AS edge_count;
```

结果只能属于以下两种正常状态：

- `0 / 0`：尚未迁移，可继续执行；
- `15 / 11`：可能已经迁移，先进行第 10 步的完整验收，不要立即重复执行。

如果只有一部分输入或边，说明数据库处于部分迁移或人工修改状态，必须停止。

### 步骤 9：执行兼容迁移

在 MySQL 命令行客户端中执行：

```sql
USE vehicle_scheduler;
SOURCE <开发者自己的项目路径>/migrate_existing_processing_chains_to_dag_compat.sql;
```

例如，项目在 `E:/Java_IDEA_Projects/RoadSimulation` 时：

```sql
SOURCE E:/Java_IDEA_Projects/RoadSimulation/migrate_existing_processing_chains_to_dag_compat.sql;
```

路径中的下划线不需要写成 `\_`。Windows 环境推荐使用 `/`，减少反斜杠转义问题。

### 步骤 10：执行后验收

#### 10.1 数量验收

```sql
SELECT
    (SELECT COUNT(*)
     FROM processing_chain
     WHERE chain_code IN (
         'CHAIN_WOOD_FURNITURE_001',
         'CHAIN_METAL_FURNITURE_002',
         'CHAIN_METAL_CAR_003',
         'CHAIN_RUBBER_CAR_004'
     )) AS chains,
    (SELECT COUNT(*)
     FROM processing_stage AS ps
     JOIN processing_chain AS pc ON pc.id = ps.chain_id
     WHERE pc.chain_code IN (
         'CHAIN_WOOD_FURNITURE_001',
         'CHAIN_METAL_FURNITURE_002',
         'CHAIN_METAL_CAR_003',
         'CHAIN_RUBBER_CAR_004'
     )) AS stages,
    (SELECT COUNT(*)
     FROM processing_stage_input AS psi
     JOIN processing_stage AS ps ON ps.id = psi.stage_id
     JOIN processing_chain AS pc ON pc.id = ps.chain_id
     WHERE pc.chain_code IN (
         'CHAIN_WOOD_FURNITURE_001',
         'CHAIN_METAL_FURNITURE_002',
         'CHAIN_METAL_CAR_003',
         'CHAIN_RUBBER_CAR_004'
     )) AS inputs,
    (SELECT COUNT(*)
     FROM processing_stage_edge AS pse
     JOIN processing_chain AS pc ON pc.id = pse.chain_id
     WHERE pc.chain_code IN (
         'CHAIN_WOOD_FURNITURE_001',
         'CHAIN_METAL_FURNITURE_002',
         'CHAIN_METAL_CAR_003',
         'CHAIN_RUBBER_CAR_004'
     )) AS edges;
```

唯一合格结果为：

```text
chains = 4
stages = 15
inputs = 15
edges = 11
```

#### 10.2 阶段约束验收

```sql
SELECT
    pc.chain_code,
    COUNT(*) AS stages,
    COUNT(DISTINCT ps.stage_order) AS distinct_orders,
    COUNT(DISTINCT ps.stage_key) AS distinct_keys,
    SUM(ps.stage_key IS NULL OR ps.stage_key = '') AS blank_keys,
    SUM(ps.processing_time_minutes IS NULL
        OR ps.processing_time_minutes <= 0) AS invalid_times
FROM processing_chain AS pc
JOIN processing_stage AS ps ON ps.chain_id = pc.id
WHERE pc.chain_code IN (
    'CHAIN_WOOD_FURNITURE_001',
    'CHAIN_METAL_FURNITURE_002',
    'CHAIN_METAL_CAR_003',
    'CHAIN_RUBBER_CAR_004'
)
GROUP BY pc.id, pc.chain_code
ORDER BY pc.chain_code;
```

每条链应当同时满足：

- `stages = distinct_orders = distinct_keys`；
- `blank_keys = 0`；
- `invalid_times = 0`。

#### 10.3 边 SKU 连续性验收

```sql
SELECT COUNT(*) AS invalid_edge_sku
FROM processing_stage_edge AS pse
JOIN processing_stage AS from_stage
  ON from_stage.id = pse.from_stage_id
LEFT JOIN goods AS from_goods
  ON from_goods.id = from_stage.output_goods_id
JOIN processing_stage_input AS to_input
  ON to_input.id = pse.to_stage_input_id
JOIN processing_chain AS pc
  ON pc.id = pse.chain_id
WHERE pc.chain_code IN (
    'CHAIN_WOOD_FURNITURE_001',
    'CHAIN_METAL_FURNITURE_002',
    'CHAIN_METAL_CAR_003',
    'CHAIN_RUBBER_CAR_004'
)
AND COALESCE(
        NULLIF(TRIM(from_goods.sku), ''),
        NULLIF(TRIM(from_stage.output_goods_sku), '')
    ) <> TRIM(to_input.sku);
```

合格结果为 `invalid_edge_sku = 0`。

### 步骤 11：启动后端并进行业务验收

数据库验收全部通过后再启动后端。验收顺序建议为：

1. 查询 4 条加工链，确认阶段顺序、输入和边正常。
2. 创建一个最小生产计划。
3. 检查反向计算结果和生产物料流。
4. 确认生产运输需求通过标准 `Shipment` / `ShipmentItem` 模型生成。
5. 确认这些需求进入现有评价体系，不使用单独评价口径。

如果发现运输主链、路线规划或前端动画异常，应停止验收并提交问题报告，不要把问题扩展为未经授权的业务逻辑修改。

## 5. 禁止使用的旧迁移方式

对已经拥有 4 条旧加工链和 15 个旧阶段的数据库，禁止直接执行：

```text
migrate_legacy_processing_chains_to_y_shape.sql
```

原因是旧阶段的 `stage_key` 为空，该脚本会将这些阶段识别为“不存在”，从而向旧加工链再次插入 15 个重复阶段。重复的 `stage_order` 会使生产计划图校验失败。

也禁止在未验收新生产链之前执行：

```text
drop_legacy_processing_execution.sql
```

该脚本会删除旧列、索引、外键和关联对象，属于不可依赖普通事务回滚的 DDL 清理。

## 6. 数据基线不一致时的处理

如果开发者的数据库不满足前置条件，按以下原则处理：

1. 只进行查询和差异报告，不立即修改。
2. 对比 `processing_chain`、`processing_stage`、`goods` 和 `poi` 的业务键，不依赖两台电脑的自增 ID 完全相同。
3. 决定以哪一侧为权威定义，再单独编写迁移脚本。
4. 禁止使用 `INSERT IGNORE`、关闭外键后强制插入，或直接复制带有自增 ID 的行。
5. 如果差异已经较大，在新数据库中恢复权威备份，不覆盖原开发库。

## 7. 整库完全同步流程

如果业务确实要求两台电脑的所有数据完全一致，应使用当前最新 `vehicle_scheduler` 的全量导出，不能使用迁移前的 `vehicle_scheduler_phase10` 作为“最新数据”。

### 7.1 数据提供方导出

```powershell
mysqldump -u root -p --single-transaction --routines --triggers `
  --set-gtid-purged=OFF `
  --result-file="D:/db-share/vehicle_scheduler_current.sql" `
  vehicle_scheduler
```

### 7.2 数据接收方创建独立数据库

```sql
CREATE DATABASE vehicle_scheduler_shared
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

### 7.3 导入独立数据库

```powershell
mysql -u root -p vehicle_scheduler_shared `
  --execute="SOURCE D:/db-share/vehicle_scheduler_current.sql"
```

导入后应先将后端配置指向 `vehicle_scheduler_shared` 进行验收，不覆盖原 `vehicle_scheduler`。

## 8. `vehicle_scheduler_phase10` 的定位

`vehicle_scheduler_phase10` 是 Phase 10 阶段的完整备份，也是本次 DAG 数据迁移前的历史基线。它的用途是：

- 核对旧加工链和阶段数据；
- 迁移失败时恢复旧定义；
- 对比评价体系合并前后的差异。

它不是当前最新数据库，不能代替迁移后的 `vehicle_scheduler` 分发给其他开发者。

## 9. Git 与数据库的边界

Git 中只包含：

- Java/Vue 源码；
- 版本化 SQL 脚本；
- 迁移和验收说明。

Git 不会自动同步本地 MySQL 中已执行后的数据。因此：

1. 合并或拉取代码不等于完成数据库迁移。
2. 每位开发者都必须在自己的数据库上执行对应 SQL。
3. `.phase10`、`mysqldump` 输出和包含业务数据的 SQL 备份不应纳入代码仓库。
4. 共享全量数据库时，应通过受控文件渠道，而不是 Git。

## 10. 其他注意事项

- 执行 SQL 前必须确认目标数据库和备份文件可用。
- 不要在命令行参数中明文写入数据库密码；使用 `-p` 交互输入或安全的本地凭据配置。
- 不要从文档中照抄他人电脑的 `D:/...` 或 `E:/...` 路径。
- 如果路径包含空格，优先使用 IDE 或 Workbench 的脚本执行功能，避免客户端路径解析歧义。
- `spring.jpa.hibernate.ddl-auto=update` 只能尝试补充表结构，不能代替业务数据迁移。
- `CREATE TABLE IF NOT EXISTS` 只能说明同名表存在，不能证明旧表的列、索引和外键完全正确。
- 迁移脚本定位为一次性规范化操作。输入和边可防重，但阶段更新会刷新 `updated_at`，不应在后续人工调整阶段后无条件重复执行。
- 数据库验收失败时先停止，不要连续运行多个修复脚本试错。
- 评价体系应继续以标准 `Shipment` / `ShipmentItem` / `Assignment` 和后端仿真时间为权威事实，不为生产物料流增加独立统计口径。

## 11. 相关文件

- `migrate_existing_processing_chains_to_dag_compat.sql`：当前基线的一次性兼容迁移。
- `create_production_domain_tables.sql`：生产计划、批次、执行和 DAG 相关表结构。
- `create_y_shape_dag_tables.sql`：旧数据库的 DAG 表与 `stage_key` 索引补充脚本。
- `migrate_legacy_processing_chains_to_y_shape.sql`：固定种子数据脚本，不用于已存在 15 个旧阶段的数据库。
- `drop_legacy_processing_execution.sql`：可选的破坏性旧字段清理，必须在独立授权和完整验收后执行。
- `doc/加工链DAG数据兼容迁移说明.md`：本机实际迁移的字段映射、执行结果和恢复说明。
