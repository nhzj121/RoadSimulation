# 沙箱正式基线数据契约 v1

## 1. 契约定位

本契约定义如何从权威来源库 `vehicle_scheduler` 生成不可变的沙箱基础数据版本。基线包不是一次可直接运行的实验场景：实验仍需在基线上选择参与对象、应用修改项、完成依赖闭包和校验，然后恢复到独立沙箱数据库。

配套数据文件为 [baseline-v1.json](baseline-v1.json)。

## 2. 版本和生命周期

- 契约版本：`baseline-data-contract/v1`
- 基线包版本：`sandbox-baseline-package/v1`
- 当前基线 ID：`roadsimulation-baseline-20260928-01`
- 2026-09-28 经明确决策，在保留旧文件副本的前提下重建了当前 v1 成果，将司机静态事实和车辆绑定纳入基线；旧副本位于 `archive/baseline-v1-pre-driver-20260928.json`。
- 此后基线发布后不可原地改写。来源数据发生业务变更时必须发布新的 `baselineId`。
- 历史实验始终引用原基线 ID、最终选中 ID 集合、修改项、随机协议和路径数据版本。
- `baselineReady=true` 只表示基础数据包通过本契约校验；`sandboxRunReady=false` 表示运行数据库恢复、路径冻结、随机协议和重演框架尚未全部实现。

## 4. 纳入字段

### 4.1 POI

纳入 `id`、名称、经纬度和 POI 类型。名称用于完整恢复和展示；坐标、类型及 ID 进入仿真事实指纹。POI 名称不是稳定业务键，关联统一使用现有主键。

### 4.2 Goods

纳入 ID、SKU、名称、类别、描述、单位重量、单位体积、温控要求、危险品等级、保质期和适配车型。SKU必须唯一；涉及运输计算的货物必须具有正的单位重量和单位体积。

### 4.3 Vehicle

只纳入静态车辆属性：ID、车牌、载重、容积、品牌、型号、车型、温控能力、危险品资质、专用车型、尺寸和适配货物。

不纳入当前状态、当前 POI、当前经纬度、当前载重、运行轮次和累计指标。默认初始位置由运行主种子在有效场景选中的 `WAREHOUSE`、`DISTRIBUTION_CENTER` 中确定；场景也可以显式提供固定初始 POI。

### 4.4 加工链

纳入加工链、加工段、多输入记录和有向连接。15个加工段的输入、输出重量比例均明确为 `1.0`。末端段允许 `outputGoodsId=null`，非末端段不允许。每条链必须只有一个末端段。

`processingPoiId` 是当前数据库结构所需的模板 POI；`requiredPoiType` 明确记录自动候选选择所使用的 POI 类型。它不表示运行时必然选择该模板 POI。加工段 `5102` 的模板 POI 为 `4762`，类型为 `TIRE_MANUFACTURING_PLANT`。

### 4.5 Driver 与车辆绑定

纳入司机 ID、姓名、电话、三项接单偏好及 `driver_vehicle` 绑定。姓名和电话用于恢复与展示；司机偏好和绑定关系进入仿真事实指纹。运行状态不从源库复制，恢复时统一为 `IDLE`。

司机不是独立可选集合。场景选中车辆后，必须自动纳入这些车辆绑定的全部司机；未绑定到入选车辆的司机不得进入有效场景。每辆入选车辆必须至少有一名司机，否则场景准备失败。Vehicle 5、10 被排除时，其六名绑定司机也随车辆闭包排除；两个未绑定司机仅保留在完整源基线中。默认有效数据因此包含 85 辆车、255 名司机和255条绑定。

偏好只用于候选排序，不得改变成本、约束、适应度或可行性。没有 `IDLE` 司机的车辆直接排除；任务启动和运行中换司机均不得产生无司机任务。

### 4.6 初始库存

本版为空。需要预置库存时，由实验场景覆盖层定义，不修改基线。

## 5. 默认不可选记录

以下记录保留在完整基线中，但默认不能进入可执行场景：

- Goods 3：单位重量和单位体积缺失；
- Vehicle 5、10：货厢容积非正；
- POI 3466：测试类型。

车辆温控能力的 `null` 原样保留为未知；v1不据此执行温控资格判断。以后启用温控实验时必须升级资格规则。

## 6. 排除范围

不纳入 Route、Customer、车辆货物匹配历史、运行期库存、运单、任务、司机运行状态及交接历史、生产计划、生产执行、评价历史和调度对比历史。

Route表不是高德路径事实集。完整路径结果以后单独版本化，由实验运行配置引用。创建时间、更新时间、修改人、自增序列和运行生成标识不进入基线。

旧 `processing_chain` 中未被当前实体定义使用的累计时间、距离和旧汇总字段不进入基线。

## 7. 场景生成与依赖闭包

实验场景必须同时保存筛选条件和筛选后确定的具体 ID 集合。恢复前至少验证：

1. 所有引用对象存在且未被默认排除；
2. 车辆初始 POI 属于本场景且类型合法；
3. 选中加工链的加工段、输入、边和模板 POI完整；
4. 加工段所需 POI 类型在场景中存在可选候选；
5. Goods物理量满足本次需求生成和运输计算；
6. 加工链只有一个末端段，边目标输入和相邻 SKU一致；
7. 未选择的数据不会被复制到运行数据库。
8. 每辆选中车辆的司机和绑定闭包完整，且不存在未绑定的有效司机。

若用户选择的 POI 集合破坏加工链依赖，准备过程必须拒绝或要求显式调整，不能静默补回未选择数据。

## 8. 指纹

采用 `lexicographic-json-v1`：对象键按 Unicode 字典序递归排序，数组使用契约规定的稳定顺序，数字按 JSON 数值序列化，`null` 原样保留，最终以 UTF-8 编码计算 SHA-256。

- `restorationPayloadSha256`：覆盖 `data` 的全部恢复字段，包括名称和描述。
- `simulationFactsSha256`：覆盖资格规则及可能影响仿真的字段，包括司机偏好与车辆绑定；排除姓名、电话、名称、描述、品牌和车牌等展示字段。

完整文件交付时还应由交付系统记录文件 SHA-256；文件哈希不写入自身。

## 9. 恢复要求

正式恢复必须写入独立沙箱数据库，不得写回 `vehicle_scheduler`。恢复保留基线主键，但不恢复原库的自增游标和逐行审计时间；数据库非空约束要求技术时间戳时，恢复器必须从基线采集时间派生固定值，不能使用每次恢复时的墙上时间。司机恢复为 `IDLE`，绑定按基线闭包恢复。准备成功后核对记录数、外键、资格规则及两个指纹，全部通过才允许将工作库标记为 `BASE_DATA_READY`。

同一场景重复准备，以及 `A → B → A` 后的两个 A，必须得到相同的初始业务事实指纹。
